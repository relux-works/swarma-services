## Enforcer, eligibility and required-body predicate — B1

The enforcing component is the builder's recipe-pinned ModuleInputVerifier, inside the existing keyless builder and BEFORE compilation. The signer independently enforces the existing frame/manifest/stream, immutable-copy and job-binding rules; it does not compile or infer graph closure from a peer assertion. No new solver, read tracer or trust service is specified.

For every supplied module record, ModuleInputVerifier requires its exact path/version directory, actual permitted material and standard Go h1 binding to the ORIGINAL source go.sum. go_mod_h1 is MANDATORY, exactly47ASCII bytes with the existing h1 form, and must equal the exact corresponding path/version/go.mod anchor. module_h1 is either exactly47ASCII bytes and equal to its original path/version anchor, or empty only for metadata-only material. Each nonempty checksum is independently checked; an empty module_h1 never makes go_mod_h1 optional. The verifier recomputes applicable standard h1 from actual supplied bytes. An original anchor is eligibility, not proof that the graph needs a body.

Define graph_required(P,V) as the pinned native Go module graph loader requesting the go.mod for that exact identity while loading this original source graph from the fresh receipt-only inputs. A requested body must be supplied and originally anchored; needed-but-unanchored is an input refusal, NEVER an omittable case. Being selected or merely occurring in original go.sum is not itself a load request. There is no separate policy oracle based on a caller's 'unused' label.

The executable graph decision is the pinned standard `go mod graph`, against that original source, exact recipe/tool/target and a fresh cache made ONLY from verified declared inputs, with GOPROXY=off, GOSUMDB=off, GOTOOLCHAIN=local, GOWORK=off, GOENV=off, GOVCS=*:off, GOAUTH=off and -mod=readonly. Require exit0 and no graph error/stderr. The native loader itself determines which bodies are loaded. A missing requested body causes offline failure; no network/cache fallback or source-sum write is possible. Implementation must not claim closure from a saved diagnostic graph or enumerate original anchors as a substitute for this operation.

A selected body's absence is allowed at the graph gate iff it has no supplied record/directory and this exact receipt-only native graph load succeeds without it. Absence remains provisional for the target: required complete compiled-module content must also be available and verified before compilation, and production success requires the fixed offline builds below. No graph pass can authorize a missing compiled module or sum. This is an operational predicate on actual inputs, not a circular future-qualification statement. Clean native load plus later fixed build, not a 'lookup disabled' string, decides success.

A claimed-but-unconsumed record is IGNORED FOR GRAPH SELECTION only AFTER all its applicable structural, original-anchor, complete-content, h1 and finite-bound checks pass. This applies to metadata-only or full records; supplying a valid extra anchored record cannot choose the selected version. A supplied unanchored, inconsistent or malformed record is refused even if the loader would not consume it. The standard loader naturally selects/ignores eligible supplied material, so no consumption tracer is required merely to reject harmless unused verified records. This explicit supplied-material policy supersedes the earlier 'required material only' wording.

Missing requested body, missing required compiled content, unanchored/wrong-sum record, unsupported material/layout, invalid source sums, inconsistent graph or failed graph load returns internal input_invalid, with no compilation/signing or artifact success. Cleanup preserves only existing operation-owned rules. Every selected operation reports its own outcome; unrelated setup failure, timeout, skipped control or arbitrary error is not proof of the intended predicate.

## Exact directory and hash domains

A metadata-only record has module_h1="". Its m/<SHA256(path+NUL+version)> directory contains EXACTLY one ordinary100644 file named go.mod and no other file/symlink/subdirectory. Standard go_mod_h1 is the standard single-go.mod checksum domain, not a hash of the outer directory name. An originally anchored generated proxy .mod body may be supplied as this go.mod; it is not a fabricated original anchor or inserted canonical module source.

A full record has nonempty module_h1 and contains EXACTLY the complete standard-canonical expanded module tree, without a separate wrapper/metadata file. Its actual canonical root go.mod is the SAME DATA entry used for the go_mod_h1 check and remains in the complete module_h1 domain. No duplicated or synthesized go.mod is inserted into that tree, and no canonical file is removed to make a checksum pass. The current MVP supports full compiled modules only when that canonical root go.mod exists. A compiled canonical module without root go.mod is explicitly unsupported and refuses input_invalid before compilation; an actually needed such form requires a separately agreed layout, never silent mutation. All22 demonstrated full modules fit this subset. A generated .mod for a metadata-only dependency remains the supported case above. No module symlink or executable entry is allowed.

Derived Go cache files may be created only from those verified inputs under the qualified pinned standard-Go rules, with complete input/derivation ledger. They are not additional trust anchors. In particular do not synthesize .info from old Time output or import acquisition .zip/.list/.info as product cache DATA. A legitimate ordinary .info-named file that is part of an authenticated source tree or a complete canonical module is still ordinary source content; the ban concerns auxiliary Go cache metadata, not a filename denylist.

## Production acceptance and diagnostic separation — N5

Production acceptance is BOTH existing fixed, pinned, offline `go build` invocations completing successfully with the required artifact/target/size, followed by the existing independent snapshot/hash/byte-equality checks and all remaining signing/audit gates. Builds use only the verified receipt inputs and explicit fixed recipe, including -mod=readonly/-trimpath, no go generate, no credentials/helper/network or toolchain download. The required-input/sum/layout/graph checks run before compilation. Missing required target content must be refused at that precompile check; a metadata-only record never substitutes for compiled contents.

A metadata diagnostic or a zero exit from `go list` is not the production acceptance operation. No Module.Error text, including 'module lookup disabled', is an allowed-success token, a trust anchor or a general tolerated-error whitelist. Preserve all diagnostic errors. A verifier that uses a metadata result as conclusive closure must establish its required claims independently; it cannot call errored JSON clean. Actual fixed offline build success and correct output remain mandatory. This document does not claim those builds or the production verifier have run.

Release Time and clean receipt-only presentation JSON are not separate requirements of this fixed build recipe. Genuine .info remains only in a separate diagnostic comparison fixture, ledgered/hash-bound rather than h1-authenticated. That fixture can establish only its compared claims and can NEVER override a signer refusal, change product input eligibility or authorize release. Any actual recipe need for auxiliary metadata returns for a separate exact-byte custody contract. No .info field, auxiliary DATA or parser exception is added.

## Decoding, source sums and refusal mapping

Retain/hash/forward the exact raw manifest body bytes, with no normalization, trim or reserialization. JSON escape variations remain legitimate. Independently, duplicate-member detection compares DECODED Unicode member names; entry-path uniqueness/collision checks, path predicates, UTF-8 byte ordering and module-record identities operate AFTER JSON unescape. Invalid Unicode/surrogates refuse. For example, {"version":1,"\u0076ersion":1} is a duplicate object member; "\u002e\u002e/file" has a parent segment and refuses; escaped backslash/NUL cannot bypass their predicates. No Unicode/filesystem normalization is silently applied; existing qualified native collision checks still apply. Decoded duplicates refuse even when raw byte spellings differ, while distinct permitted encodings with no decoded collision retain their own raw digest.

Parse original go.sum with the pinned standard Go format. For a key (module path, exact version, module versus /go.mod checksum domain), identical duplicate h1 lines may coalesce for SEMANTIC LOOKUP only; the original file bytes and hash remain unchanged. Conflicting hashes for the same key, malformed sums or an absent/wrong required anchor refuse input_invalid. Different versions and module versus /go.mod are distinct legitimate keys. Never rewrite, deduplicate or repair the source file to make validation pass.

Manifest34 decode/schema/decoded-duplicate/path/order/count failures, declared body size>4194304 before allocation, short/extra frame, DATA/hash mismatch, and receipt/anchor/layout/graph failures are classified internal input_invalid. For a current builder job, the existing refused opcode19 variant and shared-r2 mapping yield public build_failed, with zero artifact success/signing; no new client code is introduced. A signer acquisition-stage input failure uses the same public build_failed operation refusal; the separate client-request decoder retains existing invalid_request/unsupported_version behavior. If framing/binding prevents a trustworthy result frame, close the exchange and retain the internal refusal classification; never send an unsolicited/wrong-bound result. Cleanup/reconciliation uncertainty retains its existing operation gate. Actual build failure is build_failed and established isolation failure remains build_isolation_failed; artifact mismatch remains output_invalid/artifact_rejected as already specified.
