# shell-out

Manual private output capture for independently authorized commands, on Linux and macOS. The service is a standalone Go module under `src`, with no third-party dependencies. Requires Go 1.25 or later and Git when running in a Git project. It installs no runtime hooks, shell configuration, permission rules, or global commands.

Build from `src` with `go build -o <private-binary-location> ./cmd/shell-out`. Run `go test -race ./...` and `go vet ./...` there. The package exports the compiled command as `shell-out` through the existing Curator `go-v1` driver, not through a launcher-specific schema.

```sh
shell-out run --cwd . --session example -- bash -o pipefail -c 'printf "synthetic\n" | cat'
printf 'synthetic stdin\n' | shell-out run --cwd . -- /bin/cat
shell-out run --cwd . --clear-env --env PATH=/usr/bin:/bin --env EXAMPLE=synthetic -- /bin/sh -c 'printf "%s\n" "$EXAMPLE"'
shell-out run --cwd . --timeout 30s --progress 5s -- /bin/sh -c 'printf started; sleep 60'
shell-out lookup --cwd . -- 'example/ID-FROM-RESULT'
shell-out purge --cwd .
```

All options precede `--`; remaining elements are the original argv, passed without joining or quoting again. Select a shell explicitly when needed (`bash -c SCRIPT`, `zsh -c SCRIPT`, etc.). There is no implicit login shell, shell initialization, or persistent native session. Cwd is explicit; environment inherits by default, `--clear-env` starts empty, and repeatable `--env NAME=value` overrides individual values. Executable lookup uses that child's PATH and cwd. An empty PATH requires an executable path. Stdin is forwarded from the caller, including EOF. Avoid secrets in CLI arguments and session labels.

## Output and results

Every successfully initialized run creates separate stdout and stderr logs before spawning the child, including empty output and failed executable starts. Each stream's byte order is retained independently. No total ordering across streams is claimed. The final stdout preview goes to stdout, the final stderr preview goes to stderr, and the final result is one JSON object framed on stderr as `\n\x1e[shell-out result] {json}\n` (the `\x1e` denotes one literal ASCII record-separator byte, 0x1e). Progress information shares the wrapper's stderr, not the child's stderr log.

A consumer must find exactly one literal `\x1e[shell-out result] ` prefix at the start of a line and decode the single JSON object following it through EOF (allow trailing whitespace). Refuse missing, multiple, truncated or invalid frames; do not accept an unframed textual marker from a child. Child controls, including 0x1e, are escaped in previews, so child output cannot synthesize this delimiter. The frame remains wrapper metadata even when a child prints `[shell-out result]` as ordinary text. Initialization refusal has no result frame. A blocked/closed output consumer may prevent delivery; use retained metadata through `lookup` if a ref is available.

Each result includes a stable `ref` (`session/id`), the two private paths, original command exit code, signal number when applicable, command status, capture status, observed bytes, saved bytes, logical line counts, timestamps and expiry. The filenames are `YYYYMMDD-HHMMSS_<executable-slug>_<random-id>.out.log` and `.err.log`. Only a small fixed allowlist of ordinary executable basenames is used for slugs (at most 32 characters); everything else becomes `command`. Arguments and executable paths never enter the slug. There is no runtime call id available in this manual CLI; ids are 128-bit cryptographic random values, with exclusive creation and no overwrite.

- Small printable UTF-8 output (at most 4,096 bytes and 40 logical lines per stream) is printed byte-for-byte, preserving a missing final newline. Newlines and horizontal tabs are preserved; other terminal controls are escaped even in small output. Output with NUL or invalid UTF-8 is summarized as binary, never emitted as raw terminal bytes.
- Larger output uses a head and tail, each at most 2,048 **rendered** bytes and 20 lines, plus fixed markers. This limits giant lines and escape expansion. Each progress update has at most 1,024 rendered bytes and 10 lines per stream plus fixed status text. Progress shows the latest lines and repeats at the configured interval; total progress over an indefinitely running command is not a fixed-size result. Presentation uses bounded queues and drops progress when full. Each final flush has a 150 ms deadline, so undrained wrapper stdout/stderr cannot hold up timeout, signal forwarding, child cleanup or wrapper exit. A slow consumer may lose previews or the result frame; logs remain independent and presentation failure is recorded in metadata. For library callers, at most one worker per blocked presentation stream can remain blocked until the caller releases its writer.
- Default saved output is capped at 64 MiB **per stream**, configurable with `--max-capture-bytes`. This is a disk-use ceiling, distinct from preview limits. Exceeding it reports `partial`, retaining the saved prefix and a bounded in-memory head/tail of observed data until the result is presented. Captures are never described as complete after this limit, read/write/close/sync failure, or pipe-drain deadline.
- A file-open failure prevents spawn. Mid-run write failure keeps draining the child, preserves the bounded observed preview and the command's actual outcome, and reports observed and saved sizes separately. Metadata failures are reported separately in `capture_error`. Storage failures do not magically make unsaved bytes recoverable from a log.

Wrapper exit status is the original nonzero exit code when available; an actual child signal is re-raised after attempting the final result by replacing the finalized wrapper with a fixed, empty-environment POSIX shell self-signal helper (JSON also contains conventional `128+signal`). This avoids Go runtime fatal-signal traceback behavior and preserves signal termination, including QUIT and ABRT. No original command text is passed to this helper. A zero-exit command with a capture/presentation failure returns 125, as do initialization and spawn errors. **Read the JSON for command outcome versus capture outcome**; the wrapper's 125 alone does not distinguish a command that itself returned 125. Queue saturation or final-frame write/flush failure preserves the original nonzero exit or signal and the execution outcome already saved in metadata. The CLI handles SIGPIPE separately so writes to closed stdout/stderr return EPIPE through the bounded presentation path; presentation SIGPIPE is not forwarded to the child, and the child's own SIGPIPE behavior is preserved. Library callers supplying real standard-stream files must arrange their own process-wide SIGPIPE handling. The frame is enqueued as one packet, but enqueue success does not prove delivery: the consumer can still receive a missing or truncated frame and must refuse it. Metadata records presentation failures detected during capture finalization; it is not a delivery receipt for the subsequent CLI frame. File metadata remains available if storage succeeded.

## Process and TTY contract

The command runs in a new process group. INT, TERM, HUP and QUIT received by the wrapper are forwarded to the group; timeout or context cancellation sends TERM. Cancellation escalates to KILL after 250 ms. The actual direct-child exit/signal is retained even if it handles the signal and exits with another code.

When the direct child exits, remaining group members receive TERM and then KILL after a 100 ms grace period. This deliberately bounds ordinary background jobs to one invocation. Pipes get a one-second drain deadline. Programs that call setsid or otherwise detach may survive the process group; their inherited pipes trigger an explicitly partial result at the deadline, on each affected stream separately. This is not a process containment or policy enforcement service. A wrapper forcibly killed by SIGKILL cannot finalize metadata; its running record is conservatively retained and never purged automatically.

Within one explicit shell invocation, quoting, heredocs, pipelines/pipefail, cd and export work as that shell defines. They do not change the calling shell or persist into another call. File descriptors 1 and 2 are pipes, not a PTY. Programs may suppress colors, choose different buffering, disable prompts or refuse interactive use. Stdin can retain the caller's own TTY identity if forwarded directly. No terminal resize, job control, PTY emulation or persistent shell state is promised.

## Storage, refs and retention

In a Git project the destination is the project's `.temp/shell-out/<session>/`. The tool creates `.temp` if necessary, rejects tracked `.temp` contents, and checks the **exact** destinations with `git check-ignore`. Discovery, lookup and purge never create custody directories, append ignore rules, or change permissions. Run preflights the session, existing directory modes and exact destinations before bootstrap. When needed it appends `/.temp/` only to `info/exclude` anchored inside Git's common directory (including linked worktrees), refusing symlinked `info` or `exclude` before opening for append. It never edits a tracked `.gitignore`. A still-not-ignored destination is refused, including higher-priority negation rules.

Each Git invocation has a two-second deadline, process-group cancellation and a 150 ms pipe-drain bound. A blocked repository-controlled FIFO therefore causes a surfaced failure rather than an indefinite Git wait. This deadline applies per invocation, not to an entire purge sweep. If tombstone validation fails after purge has removed expired logs, the completed metadata remains and a later purge can retry the tombstone after the Git problem is repaired.

Outside Git, use the per-user cache's `shell-out` directory (Linux honors `XDG_CACHE_HOME`; macOS uses the user Library cache). Broken Git worktrees fail instead of silently falling back. The caller-selected cwd anchor is canonicalized once (including macOS system aliases). Storage traversal beneath the selected project or cache refuses symlink components, even when a symlink stays in the same tree. Descriptor-rooted operations stay anchored across renames; exclusive log creation uses no-follow flags. Capture directories are 0700 and new files 0600. Existing custody directories, including an owned project `.temp`, must already be 0700; the tool refuses unsuitable modes rather than changing them. Metadata is replaced atomically with a synced temporary file and directory sync, protected during a live run by a separate stable `.lock` inode. Failed creation cleans up its partial files. Lookup and purge also support legacy records locked on their metadata inode. Purge skips unsafe special files, symlinks and hardlinked metadata with a surfaced warning. Lookup accepts only the fixed ref grammar, never a path supplied by metadata. Same-UID adversarial processes and mount substitution are outside this MVP's containment guarantee; do not use a shared untrusted account as a security boundary.

A live record reuses its exact preflighted metadata temporary filename with exclusive creation inside its held directory handle. Completion accounting can therefore finish after a mid-run project/session rename without resolving the old absolute path through Git. Stored paths and refs still describe the original location; this does not make them portable or enable lookup/purge at a relocated location. Purge validates its own fresh temporary destination before writing a tombstone.

Retention defaults to 24 hours from completion (`--retention-hours`, positive and at most 8,760). `purge` explicitly removes only expired, completed logs inside this service's own directories, skipping locked/running records. No recursive deletion, running-file deletion, or automatic global scan occurs. Metadata tombstones and stable lock files remain to prevent ref reuse. Corrupt or undecodable metadata is retained for operator inspection while the sweep continues reclaiming other expired captures; purge prints the reclaimed count, surfaces warnings and exits 125 when any records were skipped as unsafe or corrupt. Crash-orphan temporary files/logs without usable metadata also require operator inspection and are not automatically deleted. Refs are stable only within the original absolute project/cache location: moving or renaming the project (or relocating its retained captures) is unsupported, and lookup refuses the resulting path mismatch. Lookup reports expired/unknown after expiry or removal and cannot redirect an old ref to a new capture. Purge must be invoked to reclaim expired disk usage; abandoned running records and metadata tombstones need operator inspection, so this is not an aggregate disk quota.

Logs can contain sensitive output. Investigate only needed ranges with head/tail, grep or sed. Never copy logs into reports, attachments, task resources or version control. Do not include private paths in public commit or PR text.

## Skill export and future seam

`SKILL.md` plus `agent-skill.json` implement the existing schema-8 compiled skill contract: `build_roots: ["src"]`, exported command `shell-out`, driver `go-v1`, source directory `src/cmd/shell-out`. The source build root is excluded from skill context/runtime by Curator. It uses no external dependency, build hook, compiler bootstrap or global install. The repository remains movable as one subproject.

The conventions were checked against Curator spec commit `8b34c870ab7deba99b243ba26646d68b07bb630b`, Protocol Core sections 4.2–4.3, manager section 2, and Skillfile sources section 4. A consumer selects the `shell-out` package directory from this repository at the reviewed, landed commit, records that exact source revision in its Skillfile, and resolves the exported command through its lock. The keeper handoff supplies a concrete pinned candidate Skillfile outside this repository; publication and landing remain separate steps.

Capabilities are an **audit surface**, not a sandbox for this compiled command. The manifest's fixed executable names cover Git and common shell dependencies; the purpose statement explicitly discloses arbitrary independently authorized child dispatch, inherited environment, cache storage and sensitive captures. This list must not be interpreted as granting blanket permission for child commands, denying the tool's documented effects, or establishing a runtime enforcement boundary.

Curator owns its optional generic extension rail and runtime integration. No extension profile, lock format or launcher schema is invented here. The installed Codex 0.166.0 protocol exposes hook events, but a rewrite preserving original-command authorization and shell state has not been established. Automatic capture is **unsupported/unverified** in this MVP. A future adapter must refuse if original permissions cannot be preserved. The paired known-denied/nearby-allowed permission test remains pending a real runtime seam; manual subprocess tests are not proof of that property. Claude native spill measurement is also outside this Codex-first manual MVP.
